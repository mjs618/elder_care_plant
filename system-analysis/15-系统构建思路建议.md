# 系统构建思路建议

## 1. 现状判断

当前系统最合适的定位不是“纯单体”，也还没到“全面微服务”，更准确地说是“模块化单体”。

从仓库现状看：

- 后端已经有统一应用入口、模块注册中心和动态挂载路由机制，具备模块化演进的基础。
- 前端已经有按模块做权限门禁、导航生成和路由组织的能力。
- 但领域边界还不够干净，部分模块之间仍然直接引用对方的数据模型。
- 事件总线已经接入，但还更像通知通道，尚未形成可靠的跨模块解耦层。

结论是：当前最重要的不是“继续拆服务”，而是先把模块化边界、契约和发布机制稳定下来。

## 2. 构建原则

### 2.1 先统一边界，再谈拆分

模块化的第一目标不是技术形式，而是边界清晰。

建议优先统一以下内容：

- 模块命名
- 权限命名
- API 响应格式
- 模块清单来源
- 前后端模块映射关系

### 2.2 以契约为核心，而不是以表为核心

跨模块协作应优先通过契约、事件和服务接口完成，避免直接依赖其他模块的数据库表或 ORM 模型。

### 2.3 先做可演进架构，不要一次到位追求“最终形态”

系统应该先保证：

- 能独立开发
- 能独立测试
- 能独立部署
- 能独立回滚

如果这些基础能力还不稳定，过早上微服务和微前端只会增加复杂度。

## 3. 推荐路线

### 阶段一：把模块化单体做扎实

目标：1 到 2 周内把边界、契约、权限和响应统一起来。

重点工作：

- 统一模块清单源头，后端模块注册中心作为唯一事实来源。
- 统一 API 返回结构，所有接口尽量使用统一响应模型。
- 统一权限门禁规则，所有鉴权逻辑收口到依赖注入层。
- 清理列表契约、事件类型序列化等基础问题。
- 给模块注册、路由挂载、权限校验和导航生成补测试。

阶段一的标准不是“功能更多”，而是“系统更稳定、更一致”。

### 阶段二：把跨模块副作用收口

目标：2 到 4 周内把跨模块通知和跨模块读依赖变得可控。

重点工作：

- 给事件总线补可靠性设计，至少要考虑持久化发布和失败补偿。
- 给事件消费者加幂等处理和重试策略。
- 将跨模块读依赖收口为契约客户端，不再直接访问别的模块表。
- 明确哪些协作必须同步调用，哪些必须异步事件驱动。
- 优先整理患者模块和评估模块之间的依赖关系。

阶段二的核心是把“能跑”升级成“可恢复、可追踪、可扩展”。

### 阶段三：只拆低耦合模块

目标：4 周以后再考虑独立拆分，且只拆真正适合拆的模块。

优先试点的模块建议：

- AI 助理
- 知识库
- 学习中心

不建议优先拆分的模块：

- 患者管理
- 评估管理
- 认证与租户体系

原因很简单：

- 前者耦合低，边界更容易清晰。
- 后者是系统核心，一旦拆早了，协调成本会很高。

## 4. 当前架构建议

### 4.1 后端

建议保持“模块化单体 + 事件驱动”的主路线。

推荐形态：

- 一个统一网关入口
- 一个统一认证与租户上下文
- 一个统一模块注册中心
- 各业务模块按目录隔离
- 跨模块协作优先通过契约和事件

后端不建议现在全面拆成独立微服务。

### 4.2 前端

建议保持统一壳应用，不要过早切成全面微前端。

推荐形态：

- 一个主应用壳
- 统一登录态和权限态
- 模块按路由和导航配置动态显示
- 先统一打包和发布，再评估 Federation

如果前端模块之间没有真正独立发布诉求，就不必引入微前端的额外复杂度。

### 4.3 数据层

建议继续坚持多租户隔离和统一数据治理。

推荐原则：

- 每张业务表都明确 tenant 维度
- 核心数据尽量统一 schema 规范
- 跨模块引用通过 ID 和契约，不通过直接表绑定
- 对高风险写操作保留审计和软删除机制

## 5. 风险点

### 5.1 模块清单多源漂移

如果后端模块注册、前端导航配置、权限配置分别维护，很快会出现不一致。

建议：

- 以后端为模块事实源
- 前端只消费模块清单
- 前端仅保留展示层元数据

### 5.2 事件总线看起来解耦，实际上未必可靠

如果没有 outbox、重试和幂等，事件总线只能算“通知层”，不能算真正的解耦层。

建议：

- 先补可靠性
- 再把业务协作迁移到事件驱动

### 5.3 过早拆分会放大协调成本

如果核心模块尚未稳定，就急于拆服务，会带来以下问题：

- 接口频繁变动
- 契约不稳定
- 联调成本高
- 运维复杂度上升

### 5.4 微前端不是默认答案

只有当模块真的需要独立发布、独立版本节奏时，微前端才值得引入。

否则，统一前端壳更简单、更稳、更容易维护。

## 6. 实施优先级

1. 统一模块来源和 API 契约。
2. 修正基础契约问题和序列化问题。
3. 补齐事件总线可靠性。
4. 收紧跨模块表级依赖。
5. 选择一个低耦合模块做独立部署试点。
6. 再评估前端 Federation 或更细粒度拆分。

## 7. 最终建议

这套系统最合理的路线不是“一步到位微服务化”，而是：

**模块化单体成熟化 -> 事件驱动收敛 -> 少量模块试点拆分 -> 再决定是否全面微服务化**

这样做的好处是：

- 开发效率高
- 交付节奏稳
- 风险更低
- 后续拆分成本更可控

如果系统边界已经稳定，再拆；如果边界还不稳定，先收敛。
